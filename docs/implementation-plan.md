# خطة التنفيذ المرحلية — El Khayal Motor's

## المرحلة 1 — الأساس (هذه الدفعة)

- **ما سنبنيه:** هيكل Next.js/TypeScript RTL، إعداد Supabase SSR عبر متغيرات البيئة، تدفق تسجيل/دخول/خروج/استعادة كلمة مرور، مخطط PostgreSQL أولي، RBAC قابل للتوسعة، وسياسات RLS وهيكل توثيق وتشغيل.
- **لماذا:** تثبيت أساس آمن وقابل للاختبار قبل وظائف المخزون والعملاء والبيع؛ تكلفة تصحيح الصلاحيات بعد إضافة البيانات أعلى.
- **الملفات:** `app/`, `components/`, `lib/supabase/`, `lib/auth/`, `middleware.ts`, `supabase/config.toml`, `supabase/migrations/20261118180000_foundation.sql`, `.env.example`, `.gitignore`, `README.md`.
- **تغييرات قاعدة البيانات:** جداول الملفات الشخصية والأدوار والصلاحيات والتعيينات، جدول الدراجات والوسائط وسجل التدقيق، فهارس أرقام الهيكل/الموتور، trigger لملف العميل ودور Customer، وسياسات RLS. ملف migration طُبّق يدويًا مرة واحدة على مشروع Supabase المقصود؛ سجل CLI غير متزامن ولا تعاد كتابة SQL.
- **المخاطر:** إعداد قائمة redirect URLs والبريد في Supabase مطلوب لتشغيل auth؛ تعيين أول Owner له مسار تهيئة خادمي لمرة واحدة تحت رمز مؤقت وقفل قاعدة البيانات؛ لا يُنشئه البناء ولا تُحفظ أسراره في الملفات. RLS لا يغني عن مراجعة السياسات عند إضافة عمليات جديدة. لا بيانات حقيقية أو مفاتيح سرية في المستودع.
- **الاختبار:** `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`، وفحص Git للتأكد من غياب `.env.local`. اختبارات قاعدة البيانات الحية تُجرى بعد مراجعة migration في بيئة Supabase المستهدفة.

## المراحل التالية المقترحة

2. تسوية سجل migration التأسيسي يدويًا بأسلوب tracking-only في CLI موثّق ومربوط بالمشروع الصحيح؛ لا إعادة لتشغيل SQL.
3. تطبيق migrations المعلقة بعد مراجعتها، ثم اختبارات Auth/RLS الحية وتدقيق التهيئة الأولية للمالك.
4. استكمال إدارة الفريق والصلاحيات وتطبيق migrations بعد المراجعة.
5. واجهة معالجة طلبات العملاء ثم الوسائط.
6. POS والفواتير والمدفوعات والخزينة.
7. التقارير وOCR محلي وتجهيز التخزين القابل للاستبدال.
8. مراجعة الأمان والأداء والجاهزية للإنتاج.

كل مرحلة تبدأ بتحديد النطاق والملفات وتغييرات البيانات والمخاطر والاختبار، ولا يبدأ Telegram إلا بطلب/بيانات لاحقة صريحة.

## المرحلة الحالية — الكتالوج العام

- **ما سنبنيه:** صفحات قائمة وبحث وتفاصيل للدراجات، مع صفحات فارغة واضحة إذا لم توجد سجلات؛ العرض يقرأ فقط `public_motorcycle_catalog`.
- **لماذا:** تقديم تجربة تصفح حقيقية آمنة دون اختلاق مخزون أو كشف تكلفة الشراء وأرقام الشاسيه/المحرك.
- **الملفات:** `app/catalog/page.tsx`, `app/catalog/[id]/page.tsx`, `lib/catalog.ts`, اختبارات `tests/validation.test.ts`، و`.gitignore` لاستبعاد حالة CLI المحلية.
- **تغييرات قاعدة البيانات:** لا تغييرات؛ لا إعادة تشغيل migration. الصور/الفيديو غير متاحة للعامة من المخطط الحالي، لذلك لا تُعرض حتى إنشاء مسار قراءة عام آمن.
- **المخاطر والحدود:** لا توجد بيانات مخزون معروضة في الجدول حاليًا؛ صفحة الكتالوج تُظهر الحالة الفارغة بدل بيانات مصطنعة. سجل migration الحي ما زال يحتاج مزامنة منفصلة، ولا تُستخدم `db push` قبلها.
- **الاختبار:** اختبارات تعقيم البحث وتنسيق السعر/الحالة، ثم lint وtypecheck وbuild.


## استكمال تجربة المصادقة

- **ما أُنجز:** ربط تسجيل الدخول والتسجيل برابط `next` داخلي آمن، كي يعود العميل إلى وجهته بعد الدخول أو تأكيد البريد؛ أُغلقت الروابط الخارجية ومسارات المصادقة التي قد تسبب إعادة توجيه دائرية. يظهر إنشاء الحساب من الصفحة الرئيسية والكتالوج.
- **لماذا:** مسار طلب العميل يبدأ من صفحة محمية ويجب أن يكمل بعد إنشاء الحساب، من دون السماح بتحويل المستخدم إلى موقع خارجي.
- **الملفات:** `lib/auth/redirect.ts`, `app/actions/auth.ts`, `app/auth/{callback,login,signup}/`, `components/auth-form.tsx`, `app/page.tsx`, `app/catalog/page.tsx`, واختبارات `tests/auth-redirect.test.ts`.
- **قاعدة البيانات:** لا تغييرات على المخطط الحي أو migrations.
- **المخاطر/المتطلبات:** يلزم إعداد عناوين callback والبريد في Supabase Auth. لم يُنشأ مستخدم حقيقي أو تُمنح أدوار.
- **الاختبار:** اختبارات توجيه داخلي/رفض خارجي، ثم lint وtypecheck والاختبارات والبناء.


## المرحلة — طلبات العملاء

- **ما سنبنيه:** طلب استفسار شراء مرتبط بدراجة ظاهرة بالكتالوج، وطلب استيراد بمواصفات اختيارية ونطاقات سنة/سعة/ميزانية، وصفحة «طلباتي» للعميل.
- **لماذا:** إتاحة مسارين عمليين للعميل دون اعتبار الطلب حجزًا أو بيعًا مؤكدًا، مع وصول المستخدم إلى طلباته فقط.
- **الملفات:** `app/requests/`, `app/actions/requests.ts`, `lib/requests/validation.ts`, `supabase/migrations/20261118190000_customer_requests.sql`, واختبارات التحقق.
- **تغييرات قاعدة البيانات المقترحة:** جدولان جديدان مع مفاتيح أجنبية، حالات محدودة، قيود نطاقات وفهارس للعميل والحالة. RLS يسمح للعميل بإنشاء طلب pending وقراءة طلباته فقط، ويترك القراءة الشاملة وتغيير الحالة لمن يحمل `manage_requests`. لا حذف عبر API ولا بيانات عملاء/مخزون تجريبية. ملف SQL لم يُطبق على Supabase الحي.
- **المخاطر والحدود:** تقديم الطلب لا يحجز الدراجة ولا يضمن السعر أو التوفر. نشر الواجهة قبل تطبيق الترحيل يؤدي إلى تنبيه واضح بأن القائمة تحتاج الترحيل؛ لم يتغير مخطط المشروع الحي. الطلبات ليست workflow دفع/بيع.
- **الاختبار:** تحقق وحدات لحدود الحقول ونطاقاتها، ثم lint وtypecheck وtests وproduction build. اختبارات RLS الحية مؤجلة لحين مزامنة سجل الترحيل وتشغيل migration بمراجعة صحيحة.


## المرحلة — إدارة المخزون للموظفين (مكتملة في المستودع)

- **ما أُنجز:** شاشة تعرض آخر 100 سجل مخزون، ونموذجا إضافة وتعديل يستخدمان الحقول الموجودة، مع تحقق Zod على الخادم ورسائل واضحة عند التكرار أو فشل الحفظ.
- **لماذا:** إتاحة العمل للمستخدمين المصرح لهم فقط، مع إبقاء صلاحيات العرض والإضافة والتعديل منفصلة والتحقق من الخادم بجانب RLS.
- **الملفات:** `app/admin/inventory/page.tsx`, `app/admin/inventory/new/page.tsx`, `app/admin/inventory/[id]/edit/page.tsx`, `app/actions/inventory.ts`, `components/inventory-form.tsx`, `lib/inventory/validation.ts`, `tests/inventory-validation.test.ts`, `app/admin/page.tsx`، وهذه الخطة.
- **تغييرات قاعدة البيانات:** لا تغييرات مخططية ولا SQL حي؛ تستخدم الواجهات جدول `motorcycles` وسياسات `view_motorcycles`, `create_motorcycles`, و`edit_motorcycles` في migration الأساس. يجب تطبيق ترحيلات المشروع المسجلة في المستودع في قاعدة المشروع قبل تشغيل الوظائف الجديدة. لا تُضاف سجلات افتراضية.
- **المخاطر والحدود:** الواجهة لا تمنح أي مستخدم دورًا؛ يجب إسناد الأدوار إداريًا. لا تُكتب سجلات التدقيق من هذه الواجهة، إذ لا توجد آلية كتابة آمنة منشأة لذلك بعد. لم يُختبر المسار على Supabase الحي.
- **الاختبار:** 18 اختبارًا ناجحًا، ونجح lint (مع إزالة تحذير الاستيراد غير المستخدم قبل النشر)، typecheck، production build، و`git diff --check`. لا اختبار حي ولا تعديل لقاعدة البيانات.

## المرحلة — إدارة الفريق وإسناد الأدوار (مكتملة في المستودع، غير مطبقة حيًا)

- **ما أُنجز:** واجهات Owner-only لدعوة الموظفين، إسناد/إزالة أدوار قائمة، إيقاف الحساب، تعديل صلاحيات الأدوار غير المحمية، ومراجعة آخر تغييرات الأدوار والصلاحيات؛ قراءات حالة التفعيل وآخر دخول عبر واجهة Supabase الإدارية الخادمية. التحقق من الخادم وسياسات RLS يشترطان `is_owner()`؛ أسماء الأدوار وحدها لا تمنح السلطة.
- **لماذا:** تشغيل إدارة الموظفين على RBAC الموجود مع منع ترقية المدير لنفسه أو لغيره إلى دور أعلى عبر واجهة أو Data API، وتسجيل كل تغيير دور في سجل التدقيق.
- **الملفات:** `app/admin/team/page.tsx`, `app/actions/team.ts`, `lib/team/validation.ts`, `tests/team-validation.test.ts`, `supabase/migrations/20261118193000_staff_role_management.sql`, وتحديث رابط لوحة الإدارة.
- **تغييرات قاعدة البيانات في الملف فقط:** إضافة حقول الاسم الثلاثي والموافقة، وفهرس هاتف-بريد محجوب عن أدوار العميل، وتقييد التعيين/الصلاحيات للمالك، وتدقيق تغييرات RBAC، وقصر صفحات وطلبات العملاء على دور Customer، ودالة تهيئة أول Owner محصورة بـ `service_role` مع قفل ذري. لم تُطبق هذه المهاجرة على Supabase الحية ولم يتغير سجل الترحيلات.
- **المخاطر والحدود:** يتطلب تشغيل صفحة الفريق تطبيق المهاجرة وإعداد `SUPABASE_SERVICE_ROLE_KEY` خادميًا. لا حساب موظف أو مالك حقيقي أُنشئ أو أُسند خلال التنفيذ. صفحة تهيئة المالك لا تعمل حتى تضبط قيم البيئة المؤقتة وتُطبق المهاجرة؛ الرمز المؤقت يجب حذفه فور استخدامها.
- **الاختبار:** تحقق UUID والأدوار المحمية، ثم فحوص lint/typecheck/tests/build و`git diff --check`؛ اختبارات Auth/RLS الحية مؤجلة حتى تسوية سجل الترحيل وتطبيق التغييرات بعد مراجعة.


## توضيح متطلبات هوية المالك والعملاء

- التسجيل العام يقبل Customer فقط، ويطلب الاسم الأول والأوسط واسم العائلة والهاتف والبريد وكلمة المرور وتأكيدها وموافقة صريحة على الشروط والخصوصية. يظل تأكيد البريد ومسار العودة الآمن محفوظين. لا يوجد خيار لتسجيل موظف أو مدير أو مالك.
- تسجيل الدخول يقبل الهاتف المصري أو البريد مع كلمة المرور؛ ربط أرقام حسابات البريد ببيانات تسجيل الدخول محفوظ بخادم التطبيق فقط بعد تطبيق migration إدارة الفريق.
- واجهات `/account` و`/requests` لا تقبل إلا دور Customer؛ فحص الخادم وسياسات RLS تمنع الموظفين والمالك من دخولها أو إنشاء طلب عميل. الدعوات وإدارة الفريق والصلاحيات وسجل تغييرات RBAC محصورة بالمالك في فحص الخادم وRLS.
- رقم دخول المالك يُضبط فقط في `OWNER_BOOTSTRAP_PHONE` على الخادم. لا تُحفظ كلمة مرور أو رمز تهيئة ثابت في المستودع أو الكود. التهيئة الأولى خادمية لمرة واحدة وتحتاج رمزًا مؤقتًا قويًا يضبطه المشغّل خارج Git ثم يحذفه بعد النجاح. لا حساب أو دور Owner حي أُنشئ بهذا التغيير.
- نسختا شروط الاستخدام والخصوصية أوليتان وتحتاجان اعتماد المالك والمراجعة القانونية قبل الإطلاق.
